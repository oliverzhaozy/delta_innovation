## Observed structure (renderer-facing facts)

1. **Date header:** `Routine Orders for DDMMYY` then the weekday name on its
   own line (190626 = Friday 19 Jun 2026 ✓).
2. **Section order:** header → Duty Personnel → timeline → Safety Matters →
   Administrative Matters → Logistic Matters → Security Matters → R&D
   Matters → Instructions → Messages and QOTD → Key events of the week.
3. **Duty Personnel:** `CDO/CDS: <RANK> <NAME IN CAPS>` then
   `COS: <RANK> <NAME IN CAPS>`. Note the label is **CDO/CDS** here, not the
   app's elsewhere-label "CDO/S".
4. **Timeline:** blocks of `HHMM` + `H` (e.g. `0600H`) or `TBC`, each
   followed by one `- item` line per activity; blank line between blocks.
   The TBC block in the sample sits BETWEEN 1100H and 1800H, not at the end.
5. **Matter sections:** each is a header line + `- ` bullet lines. Empty
   sections (Logistic Matters, Instructions in this sample) render a bare
   dash line.
6. **Messages and QOTD:** quoted message + `- <attribution>` pairs; the two
   quotes carry an extra author line before the attribution.
7. **Key events of the week:** `Mon`/`Tues`/`Wed`/`Thurs`/`Fri` (note the
   spellings) + ` - ` + comma-joined items; covers the week containing the
   RO's own date. No separator line between QOTD and this section.
8. **Separators:** ➖ runs of varying length (13/12/9+space+3), some with
   trailing spaces; several headers also carry trailing spaces.

## Owner decisions (P5.1 gate, answered 2026-07-07)

- **(l) Normalize separators and whitespace.** The renderer emits a uniform
  12-➖ separator and no trailing spaces; the sample's irregular runs are
  hand-typing artifacts, not format. Bullet characters INSIDE keyed content
  (e.g. Security Matters' `⁃`) are data and pass through untouched.
- **(m) Duty label is `CDO/CDS:` in the RO only** (the rest of the app keeps
  CDO/S). Names render `RANK FULL NAME` in caps, e.g. `COS: CPL ANG CHENG ZE`.
- **(n) Timeline = standing items + auto-inserted TP events + hand-keyed
  extras.** Owner's words verbatim: *"TP calendar event should auto-insert.
  The 0600 Roll call and TBC for LP is standard for all days. On every last
  day of the week (fridays, unless there is public holidays or otherwise
  stated)."* Reading (confirmed against the Friday sample, whose TBC block is
  `SBA, LP`): `0600H — Roll call & Breakfast` and `TBC — LP` are standing
  DAILY items; `TBC — SBA` is standing on the LAST WORKING DAY of the week
  (Friday, or earlier when Friday is a public holiday — the public_holiday
  table decides). Standing items live as S3-editable rows, so "otherwise
  stated" weeks are a data edit, not a code change.
- **(n′) TBC placement (renderer decision, deterministic):** timed blocks
  ascending by time, then ONE `TBC` block last. The sample's mid-list TBC was
  hand-placement; a derived document needs a deterministic rule. Within the
  TBC block: standing items by their position, then extras in keyed order.
- **(p) RO edit rights are WIDE (owner decision 2026-07-07, overrides P5.4's
  "same person next day 403s" Done line):** any command-team appointment
  (OC/SM/2IC/PC/P2IC/PS) may edit any day's RO — `policy.can_edit_ro` stays
  exactly as P4.8 landed it. Since every CDO/S-eligible appointment is
  command team, the A9 duty window is currently subsumed by the fallback; the
  window plumbing stays (harmless, and the rule may narrow later).
- **(o) Standing vs daily:** the six Matters sections (Safety,
  Administrative, Logistic, Security, R&D, Instructions) are standing
  boilerplate, S3/admin-edited; an empty section renders a bare `-` line.
  Daily: the timeline extras and **Messages and QOTD pasted as ONE free-text
  blob** (its internal quote/attribution structure is not parsed). Weekly:
  Key events (Mon–Fri, spellings `Mon/Tues/Wed/Thurs/Fri`), covering the week
  containing the RO's date; no separator line between the messages blob and
  the key-events block. Duty Personnel is derived (assigned rows dated the
  RO's date — A9, read as decision (x) 2026-07-27 leaves it: rows are live on
  write, so there is no CONFIRMED state to filter on; a date with no duty row
  renders an explicit placeholder, never a silent blank).

## Revision 2026-07-24 — standing items removed, key events derived (A11)

Owner decision, superseding parts of (n) and (o); spec in
`docs/superpowers/specs/2026-07-24-ro-derived-key-events-design.md`.

- **Standing timeline items are gone.** The timeline is TP events starting
  on the day + hand-keyed extras only; the former standing lines (0600H
  Roll call & Breakfast, TBC LP, TBC SBA) are keyed as extras when wanted.
  (n′)'s block rules are unchanged.
- **Key events are derived from the TP calendar, never hand-keyed.** Each
  weekday's line lists the titles of TP events overlapping it (start date ≤
  day ≤ end date): events starting ON the day first, time-ascending, then
  continuing multi-day events by start — the sample lists the week-long
  backdrop last on every line. A weekday with no overlapping TP event shows
  the public holiday's name if it is one, else **"Garage Maintenance"**. A
  holiday that has TP events shows just the events.

## Revision 2026-07-28 — which TP events reach the document

Owner decisions refining the 2026-07-24 revision's TP feed.

- **Course-labelled TP events never enter the RO.** An event carrying
  `TpLabel.ON_COURSE` (value `Course`) is excluded from the whole document —
  not the timeline, not the key-events block. A course conduct's effect on
  the company is its participants' absence, surfaced by the parade/presence
  pipeline, not a company activity to publish. Every other TP event (any
  other label, or none) is unaffected. The exclusion lives in the ONE
  `ro_service.build` TP query, so both consumers inherit it; `domain/ro`
  stays ignorant of calendars and labels.
- **An all-day TP conduct joins the TBC block, not `0000H`.** An event with
  `all_day` set carries no keyed timing (its stored bounds are 00:00 →
  23:59:59.999999 per `domain/events.all_day_bounds`), so publishing `0000H`
  would announce a start time nobody keyed. Within the TBC block the order is
  all-day conducts by start, then the hand-keyed extras in keyed order. The
  starts-on-the-day rule is unchanged: a multi-day all-day conduct appears in
  the timeline only on its start day — its later days are carried by the
  key-events block.
- **The RO exists only for weekdays.** The page defaults to the next weekday
  (tomorrow, or Monday across a weekend), the prev/next arrows step over
  Sat/Sun, and a hand-keyed weekend URL rolls forward to that Monday — so no
  weekend RO document can be created or edited. Public-holiday *weekdays* are
  deliberately not skipped: they still carry an RO, whose key-events line names
  the holiday and whose missing-duty warning covers a holiday duty gap. The
  weekend step lives in `domain/dates.next_weekday`/`prev_weekday` (weekend-only
  by design — no holidays parameter, unlike leave's `working_days`).
