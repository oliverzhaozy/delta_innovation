# SKILL BLUEPRINT — Python / Flask / SQL (Server-Rendered)

**Scope:** Flask + SQLAlchemy + SQLite/Postgres + Jinja server-rendered HTML. No SPA framework.
**Contract:** Follow every rule below as a hard constraint. When a rule conflicts with convenience, the rule wins. When a rule conflicts with an explicit user/repo instruction, the instruction wins — log the deviation in one line.

---

## 1. GOLD STANDARD ARCHITECTURE

### 1.1 Folder layout (canonical)

```
project/
├── app/
│   ├── __init__.py          # create_app() factory ONLY. No routes, no logic.
│   ├── extensions.py        # db, migrate, login_manager, csrf — instantiated unbound
│   ├── models.py            # SQLAlchemy models + enums. No business logic beyond invariant helpers.
│   ├── domain/              # PURE modules. Zero Flask imports. Zero I/O. The core asset.
│   │   ├── policy.py        # authorization predicates (who may do what)
│   │   ├── <concept>.py     # one file per business concept; functions take/return plain data
│   ├── blueprints/          # one blueprint per domain area == one URL prefix
│   │   └── <area>/
│   │       ├── routes.py    # thin view functions: parse → authorize → call domain → render
│   │       └── forms.py     # WTForms (validation shape only, not business rules)
│   ├── templates/
│   │   ├── base.html
│   │   └── <area>/          # mirrors blueprint names exactly
│   └── static/
├── migrations/              # Alembic, autogenerated then HAND-REVIEWED
├── tests/
│   ├── conftest.py          # app fixture (factory, in-memory or tmp DB), client fixture
│   ├── test_domain_<x>.py   # pure-function tests, no HTTP — the majority of tests
│   └── test_routes_<x>.py   # thin HTTP tests: status codes, authz, redirects
├── instance/                # runtime DB, gitignored unless repo policy says otherwise
├── config.py                # classes: Config, TestConfig; secrets via env only
└── .flaskenv
```

### 1.2 Non-negotiable separation rules

- **Domain purity:** `app/domain/*` never imports `flask`, `request`, `current_app`, or models with live sessions. Functions accept primitives/dataclasses/model instances and return values or raise domain exceptions. Rationale: pytest hits all logic without HTTP; views become untestworthy glue.
- **Thin views:** a route function does at most: (1) parse/validate input, (2) authorization check, (3) one domain call or one transaction, (4) flash + render/redirect. If a view exceeds ~30 lines, logic is leaking — extract to `domain/`.
- **One writer per invariant:** every business invariant (balance, uniqueness, state machine transition) is enforced in exactly one function, and that function owns the transaction boundary.
- **Naming:** blueprint name == folder name == template subfolder == URL prefix. Enum identifiers are distinct even when display strings collide (two concepts that print the same MUST NOT share an enum member).
- **No stored derivations:** anything computable from source rows (balances, availability, counts) is computed by query at read time. Storing it creates a second source of truth that WILL drift.

## 2. CRITICAL EDGE CASES — TOP 7 FAILURE MODES

### EC-1: Check-then-act race (TOCTOU) on balances and uniqueness
**Failure:** `if balance >= cost: insert deduction` — two concurrent requests both pass the check; balance goes negative. Same shape: pre-checking uniqueness with a SELECT before INSERT.
**Prevention:**
```python
# Uniqueness: constraint + catch, never pre-check
try:
    db.session.add(row); db.session.commit()
except IntegrityError:
    db.session.rollback(); raise DomainConflict(...)

# Balance: decide and write in ONE transaction; SQLite: take the write lock up front
with db.session.begin():
    db.session.execute(text("BEGIN IMMEDIATE"))  # SQLite only; Postgres: SELECT ... FOR UPDATE
    balance = db.session.execute(select(func.coalesce(func.sum(Ledger.delta), 0))...).scalar()
    if balance < cost: raise InsufficientBalance(...)
    db.session.add(Ledger(delta=-cost, ...))
```
**Validation:** a test that performs the operation twice with the same precondition must produce exactly one success.

### EC-2: Denormalized state drift
**Failure:** approval writes `status=APPROVED` AND a `balance` column AND a calendar row — three writes that can partially fail or be edited independently.
**Prevention:** append-only ledger; `balance = SUM(delta)`; corrections are compensating REVERSAL rows, never UPDATEs; absences derived by querying approved requests. The approval is ONE transaction that writes status + ledger row atomically.
**Validation:** grep the schema for any column whose value is computable from other rows; each hit is a defect.

### EC-3: N+1 lazy loads triggered inside Jinja
**Failure:** view passes a list of parents; template loops `{{ req.person.name }}` — one query per row, invisible in code review.
**Prevention:**
```python
rows = db.session.scalars(
    select(LeaveRequest).options(selectinload(LeaveRequest.person))
).all()
```
**Validation:** test with `sqlalchemy` event listener counting statements; assert count is O(1) w.r.t. row count for every list page.

### EC-4: Missing object-level authorization (IDOR)
**Failure:** `@login_required` present, but `/request/42/approve` never checks the actor may act on request 42. Mid-tier models check *authentication* and role, not *object ownership/routing*.
**Prevention:** deny-by-default helper used in every mutating route:
```python
def authorize(actor, action, obj):
    if not policy.allows(actor, action, obj):  # pure function in domain/policy.py
        abort(403)
```
Self-approval and cross-scope access are forbidden structurally in `policy.py`, not by UI hiding.
**Validation:** for every mutating endpoint, a test where a wrong-but-authenticated user gets 403.

### EC-5: Module-level mutable state / app-factory violations
**Failure:** module-level `app = Flask(__name__)`, module-level caches/dicts, or config read at import time. Breaks test isolation and leaks state across requests within a worker.
**Prevention:** unbound extensions in `extensions.py`, bound inside `create_app()`; per-request state only on `g`; no module-level mutable containers. Late-binding closure trap when registering routes in loops: bind with default arg `lambda x=x: ...`.
**Validation:** `create_app(TestConfig)` twice in one process must yield two independent apps; import of any `app.*` module must have no side effects.

### EC-6: Datetime/timezone arithmetic errors
**Failure:** mixing naive and aware datetimes; using `datetime` where `date` semantics are meant; counting calendar days when the rule is working days; DST assumptions.
**Prevention:** ONE documented time policy per project (e.g., "all naive, local to X" or "all UTC-aware"), enforced at the boundary. Use `date` (not `datetime`) for date-only logic. Working-day counts go through a single pure function that consults the holiday table; nobody subtracts dates inline.
**Validation:** property/golden tests on the date function covering: weekend spans, holiday-adjacent spans, single-day, half-day, and year boundaries.

### EC-7: SQLite production defaults left unfixed
**Failure:** "database is locked" under trivial concurrency; foreign keys silently unenforced (SQLite default is OFF); WAL never enabled.
**Prevention:** per-connection pragmas via engine event:
```python
@event.listens_for(engine, "connect")
def _set_pragmas(dbapi_conn, _):
    cur = dbapi_conn.cursor()
    cur.execute("PRAGMA foreign_keys=ON")
    cur.execute("PRAGMA busy_timeout=5000")
    cur.close()
# WAL set once at DB creation: PRAGMA journal_mode=WAL
```
**Validation:** a test inserting a child row with a dangling FK must fail; it passing means pragmas are not applied.

**Honorable mentions (check, don't skip):** float arithmetic for money/quota (use integers in smallest unit); `|safe` or `autoescape false` in Jinja (XSS); missing `db.session.rollback()` in teardown (poisoned session for the next request); debug server / `DEBUG=True` reachable in deployment.

## 3. STEP-BY-STEP IMPLEMENTATION PIPELINE

Execute phases strictly in order. Do not begin phase N+1 with phase N incomplete.

**Phase 0 — Read before write.** Read the spec/plan and existing code for the area. List: entities touched, invariants involved, permission rules in force. If a repo plan document exists, it overrides your defaults.

**Phase 1 — Schema & types.** Define/alter models, enums, constraints FIRST. Every invariant that CAN be a DB constraint (unique, check, FK, not-null) MUST be one. Generate migration; hand-read the migration diff before applying.

**Phase 2 — Pure domain functions.** Write the business logic in `domain/` as pure functions with explicit inputs/outputs and typed domain exceptions. No Flask, no session commits inside.

**Phase 3 — Tests against domain.** Write pytest cases for the pure functions: happy path, each boundary from the invariant list, each exception path. Golden tests for any generated text output. Run; all green before any route exists.

**Phase 4 — Transaction layer.** Write the thin service that opens the transaction, calls the domain function, and commits — one function per user-visible action. Concurrency posture per EC-1 decided here.

**Phase 5 — Routes & forms.** Thin views only (parse → authorize → service call → render). Every mutating route: CSRF-protected POST, object-level authz per EC-4.

**Phase 6 — Templates.** Server-rendered Jinja; eager-load everything the template iterates (EC-3); autoescape on; no logic beyond display formatting.

**Phase 7 — Error boundaries & verification.** Map domain exceptions → flash + redirect or 4xx; verify 403/404 paths by test; run the FULL test suite, not just new tests; then commit with a message naming the task.

## 4. REASONING RULES (META-RULES — APPLY BEFORE ANY CODE)

- **R1 — State-mutation sketch first.** Before writing executable code, enumerate every row INSERT/UPDATE/DELETE the feature performs, grouped by transaction. If any user action maps to >1 transaction, redesign until it is 1, or explicitly justify why partial failure is acceptable.
- **R2 — Invariant ledger.** List every invariant the change touches ("balance never negative", "one X per person per day", "state machine A→B only"). For each, name the single function/constraint that enforces it. An invariant with two enforcers, or zero, is a design bug.
- **R3 — Dependency walk.** Before editing a function, grep all call sites and all templates referencing the routes/fields involved. Changing a return shape or enum without walking dependents is forbidden.
- **R4 — Concurrency question is mandatory.** For every write path ask: "what happens if this runs twice, interleaved?" Answer with a mechanism (constraint, single transaction, lock), never with "unlikely at this scale."
- **R5 — Derivation test.** Before adding any column or stored value, ask: "can this be computed from existing rows?" If yes, do not store it — query it.
- **R6 — Authorization is per-object, not per-role.** For every endpoint, state WHO may act ON WHICH object, and encode it as a pure predicate. UI hiding is not authorization.
- **R7 — Warn vs block discipline.** Business-rule tension (conflicts, low manning, overlaps) → surface a warning to a human decider. Only data-corruption risks (double-write, ineligible assignment, constraint violation) hard-block. Never silently auto-resolve.
- **R8 — Boundary enumeration before tests.** For any date/quantity logic, write down the boundary set (empty span, single unit, half unit, weekend/holiday adjacency, year rollover, maximum) BEFORE writing tests, then write one test per boundary.
- **R9 — One-line "why" per decision.** Every non-obvious design choice gets a single-line rationale comment at decision level (module/function docstring), never line-by-line narration.
- **R10 — Stop conditions.** Pause and ask the human when: an invariant conflicts with the spec, a migration would lose data, or a permission rule is ambiguous. Everything else: decide, note the rationale, proceed.
