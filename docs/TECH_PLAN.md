# Delta Innovation — Technical Implementation Plan

> Approved 2026-07-05. `[REVISED 2026-08-03 — cleanup: build status]` All phases P0–P10 are built; the app is deployed at coyadmin.duckdns.org and, per decision (gg) of 2026-08-02, runs the real roster. The task breakdowns below are the historical build record: read them for the reasoning, not as work outstanding, and treat every dated revision marker as the current rule.

## Context

Delta (a ~36-person Singapore military company) runs manpower admin on TimeTree plus hand-assembled text documents. The core failure: leave approval, calendar plotting, and balance deduction are three separate manual steps, so S3's OFF/OIL tracking drifts. This app **replaces TimeTree as the single source of truth**: final approval of a leave request is the one action that both plots the absence and decrements the balance. Parade states, duty rosters, RO, manning, and meal counts are all generated from the same data; anything manpower-critical is decision-support — the app proposes, a human confirms. Stack fixed: Python + Flask + SQLite + server-rendered Jinja. ~40 users, internet-reachable, deliberately baseline security. Partly a learning project — significant decisions carry a one-line "why".

This plan was pressure-tested by a 5-critic review panel (ambiguity, edge cases, design red-team, MVP scope, security); its confirmed findings are folded in below.

## Assumptions that would change the design

1. **No TimeTree import** — app starts fresh; S3 keys opening OFF/OIL balances at rollout.
2. **Ledger deduction counts working days only** — weekends/PHs inside an approved range plot as away but deduct zero. Approver sees the breakdown ("Fri–Mon = 2 OFF deducted").
3. **Balances in integer half-day units** (full day = 2); half-day requests are single-day only; AM+PM same day merges to a full-day deduction.
4. **Parade-state reference times** (pinned finally by the format samples): evening COS message compiled on D−1 forecasts day D; roll call covers the night; morning parade covers first parade of day D.
5. **No per-soldier self-declaration flow** — the COS keys exceptions (self-declaration is a v2 candidate).
6. **No notifications** — WhatsApp remains the unit's channel; approvers get dashboard queue badges. Telegram bot is the v2 answer if latency bites.
7. **No approval delegation in v1** — the app is reachable anywhere, so an OC on leave can still approve from a phone; if that proves unrealistic, add a "2IC acts for OC" toggle later.
8. **Accounts admin-provisioned** (S3 + developer as `is_admin`); no self-signup; admin-driven password reset. `[REVISED 2026-08-02 (owner): the command team is ALWAYS admin — policy.is_admin returns True for any COMMAND_TEAM appointment (PS and above), so the stored is_admin column is only the manual grant for Det Comd/Opr (S3 and the developer). Approval authority is unaffected: it comes from appointment, never from admin.]`
9. **Single company, single timezone (Asia/Singapore, naive datetimes), trusted-insider threat model, mobile-first usage.**
10. **Hosting this data on a commercial VPS is acceptable to the chain of command** — gated by an explicit task (P0.7) to get the OC's written OK *before* deployment. If refused: same app behind Tailscale/WireGuard, not a rebuild. `[REVISED 2026-08-02 by decision (gg): discharged — the organisation approved the project, so the P0.7 gate that decision (k) had folded into that approval is closed and the assumption is confirmed, not pending. ## Spec pressure-test

### Weakest links / hidden complexity
- **Parade-state semantics** are the app's real complexity: 3 variants × AM/PM × stay-out × date-ranged statuses × duty personnel. Resolution: one pure engine with a fixed **precedence rule** (approved leave > out-of-camp status > **course** > duty > stay-out > present; course inserted 2026-07-26 — a keyed status is deliberate, a derived course cover is inferred; the `deactivated` top tier was removed 2026-07-30 by decision (dd), which deletes posted-out people outright), exactly one line per person per parade, **duty overrides stay-out at night**, conflicts surfaced to the COS instead of silently resolved. *(The per-line COS override was built as drag-and-drop recategorization in P8, removed 2026-07-26 by owner directive, and* `[REVISED 2026-07-26]` *reinstated the same day in P10 with a different UX: the drag surface is the rendered message itself, not a separate grid, and a drop against keyed data asks for confirmation first. The engine is untouched — an override is a separate* `parade_override` *row applied inside* `build_doc` *between categorize and render, so the derivation is never edited and Reset restores it byte-for-byte.)* Heavily unit-tested; the highest-risk phase (3) is split in two.
- **Eligibility pool gaps**: a 3SG PS satisfies *neither* duty rule (COS needs rank ≤ 2SG + Det Comd/Opr; CDO/S needs rank ≥ 2SG + PC/P2IC/PS) — and Delta's PSs are NSF. The rules are applied exactly as written, but the roster page **shows the computed pools** so an accidentally tiny/empty pool is visible immediately.
- **The TU Det Comd trap**: manning slot "TU Det Comd" = appointment P2IC/PS, disjoint from company appointment Det Comd (whose holders fill Det Personnel). Distinct enum identifiers, an explicit slot→appointments mapping table, UI label "TU Det Comd (P2IC/PS)", and a regression test asserting the trap.
- **Leave lifecycle after approval** (spec-silent, all handled): full cancellation with compensating ledger credit (Phase 1); early return / partial amendment with prorated credit (Phase 2); leave approved after a roster/manning is confirmed → flag the conflict, never auto-reassign; edits to a pending request reset it to the start of its route.
- **Retroactive drift in generated documents**: live-recomputed documents change when history changes. Cheap fix: parade states get a **finalize snapshot** (rendered text + who/when) at copy time from Phase 3a. `[REVISED 2026-07-26 (owner): the snapshot fix is gone — built in P3a.8, removed 2026-07-11, re-introduced 2026-07-24 and removed again 2026-07-26. Every document is re-derived on every request and the drift is ACCEPTED: the pasted WhatsApp message is the archival record of what was sent.]`

## Architecture

### Why SQLite
One file, zero administration, real transactions. 40 users producing a few writes a minute is orders of magnitude under its limits; WAL lets reads proceed during writes; backup = one `.backup` command. A client-server DB here is pure ops burden.

### Layout
```
app/
  __init__.py        # create_app() factory — per-test app instances, clean config split
  extensions.py      # db, login_manager, csrf, limiter
  models/
  domain/            # PURE modules, no Flask imports — the testable core
    policy.py        #   RBAC predicates (appointment/company_role/is_admin + duty-of-day)
    eligibility.py   #   COS/CDOS/TU-slot predicates + availability
    presence.py      #   who is where on date D (absences × statuses × stay_out × duty)
    parade.py        #   compute(date, variant) -> one line per person + counts
    roster.py        #   greedy monthly generator (hard/soft constraints)
    meals.py         #   day/overnight presence counters
  blueprints/        # auth, admin, leave, ledger, calendar, parade, duty, ro, manning, meals
  templates/  static/
migrations/  tests/  seed/  config.py  wsgi.py
```
*Why blueprint-per-domain: each maps to one user-facing job and one build phase; routes, templates, and permissions stay cohesive. Why pure domain modules: the hard part is date/status arithmetic — keep it out of view functions so pytest hits it without HTTP.*

### Auth & sessions
Flask-Login cookie sessions (httpOnly, Secure, SameSite=Lax) · werkzeug password hashing · Flask-WTF CSRF on every form · Flask-Limiter on login (in-memory is fine; per-worker counters accepted) · **session cleared and rotated at login and logout** (fixation) · forced password change on first login (min length 12, no complexity theatre, no rotation) · remember-me for phones · admin reset. **Deny-by-default authorization**: a `@require(policy)` decorator on every route plus **object-level checks** (leave/ledger lookups verify the viewer is the requester, their approver, or S3 — the realistic breach here is IDOR, not crypto). `[REVISED 2026-07-09 by decision (b): the platoon half of this line — "a PC passes is_pc but must also match the request's platoon" — is gone; any PC may approve any PENDING_PC request. Self-approval stays structurally impossible, and the requester/approver/S3 object checks are unchanged.]` Rotating-duty rights (COS keys parade, CDO/S edits RO) resolve via `duty_assignment` for that date, with PS/S3 fallback. No 2FA/SSO/WAF — gold-plating for this threat model.
*Why Flask-Login + werkzeug + Flask-WTF: boring, maintained, zero extra services; CSRF is baseline (not gold-plating) for a cookie-auth form app on the internet.*

### The core transaction (approval auto-plots + auto-decrements)
1. Requester (NSF) submits → PENDING_PC (PS and below) or PENDING_OC (PCs). Form shows their own balance; overlaps with their existing requests warn at submission.
2. Any PC reviews (`[REVISED 2026-07-09 by decision (b)]` — this line read "PC (matching platoon only)"; own-platoon scoping was removed, a PC's own request skips this step): panel shows current balance, deduction breakdown, conducts they're tagged in on those dates (Phase 2+), duty assignments (Phase 4+), manning membership (Phase 6+), overlapping absences, projected away-count per requested day. Approve → PENDING_OC; reject with remark.
3. OC approves → **one DB transaction**: conditional `UPDATE … WHERE status='PENDING_OC'` (rowcount 1 or abort — beats double-click/concurrent approvals), balance and overlap **re-checked inside the transaction**, status → APPROVED + ledger debit rows (OFF/OIL only; working days only). Commit or nothing.
4. Every downstream view derives from APPROVED requests — away immediately, no second step. *This transaction IS the product.*
5. Insufficient balance: loud warning with projected negative; OC may still approve (human decides); negatives flagged on S3's page. Hard-block only a same-day-part double-deduction (data corruption, not judgment).
6. Cancellation (Phase 1): requester cancels pending freely; approved leave is cancelled by S3/OC → status CANCELLED + compensating REVERSAL credit in one transaction. Early return (Phase 2): amend end_date + prorated credit. Ledger stays append-only.

### Document generation
All documents (3 parade variants, RO, roster, manning) are **Jinja text templates** over query results rendered into `<pre>` with a copy button (small vanilla JS — no framework case exists in this app). Deterministic ordering: platoon → rank order → name. `[REMOVED 2026-07-26: owner directive — parade states no longer freeze to parade_snapshot on copy; every document is re-derived on every view]` *Why text: these are WhatsApp messages today; matching the exact current format is the requirement.*

### Deployment (VPS shape; host: GCP always-free e2-micro per decision (w))
GCP e2-micro, US region (free-tier constraint — decision (w)) · gunicorn `-w 2 -k gthread --threads 4` bound to **127.0.0.1** (SQLite is single-writer; 8 concurrent requests is ample) · **ProxyFix** (x_for/x_proto/x_host=1 — Secure cookies and rate-limit keying are wrong without it) · Caddy reverse-proxy with auto-HTTPS, `reverse_proxy` only (no file_server near the app tree) · systemd (Restart=on-failure, EnvironmentFile 600 with a real SECRET_KEY — app refuses to start on a missing/placeholder key or debug=True, TZ=Asia/Singapore) · DB in `/var/lib/<app>` chmod 600/dir 700 (WAL needs directory write) · pragmas per connection: foreign_keys=ON, busy_timeout=5000, synchronous=NORMAL; journal_mode=WAL once · nightly `sqlite3 .backup` (never cp a live WAL DB), **encrypted with age before leaving the box**, monthly restore drill · ufw default-deny (22/80/443), key-only SSH, unattended-upgrades, non-root service user.

## Permission layers (two distinct concepts)

**1. App access (RBAC)** — *what you can see and do.* Pure predicates in `domain/policy.py` from appointment + company_role + is_admin (+ duty-of-day), enforced by route decorators and object-level checks. Everyone: request leave, own history, view TP, declare overseas. Command team (OC..PS): ARCTIC, event CRUD. PC: first-step approval of any PENDING_PC request (`[REVISED 2026-07-09 by decision (b)]` — "own platoon only" removed). OC: final approval. S3: ledger, manning, people data (`[REVISED 2026-07-26]` — direct absences removed with the `direct_absence` table; regulars' off/leave lives in ARCTIC FOE). S4: meals. PS (all three): duty roster. COS-of-day: parade keying. CDO/S-of-day: RO. Admin: accounts, holidays.
*Why code, not DB tables: permissions are a pure function of appointment; an editable permission matrix is config with no configurer at 40 users.*

**2. Assignment eligibility** — *who can be picked.* Pure predicates in `domain/eligibility.py` over rank + appointment:
- `eligible_cos`: rank ≤ 2SG **and** appointment ∈ {Det Comd, Opr}
- `eligible_cdos`: rank ≥ 2SG **and** appointment ∈ {PC, P2IC, PS} (2SG legally sits in both rules; the appointment sets are disjoint, so nobody is dual-eligible)
- TU slots via mapping table: TU Comd {OC, 2IC} · TU Planner {PC} · **TU Det Comd {P2IC, PS} — not company Det Comd** · Det Personnel {Det Comd, Opr}
- `available(p, date)`: no approved absence or blocking status touching the date (incl. half-days, per answer d), not tagged in an overnight/outstation TP event, not already on the other duty. `[REVISED 2026-07-28 by decision (z): TP events no longer block — duty_service passes no events, so only a covering absence or the other duty skips a person.]`

Eligibility ∧ availability feeds auto-pick; humans always confirm; manual assignment over a warning is allowed; hard-block only rule violations (a PC can never hold COS). Never auto-reject, never silently reassign.

### A. Blind spots — task amendments (things that would break as originally written)

**A1 — Breakfast's duty term is presence-derived or it is wrong (amends P4.7).** Once CONFIRMED duties feed `presence.resolve`, duty stayers land in roll-call CURRENT STRENGTH via `PresenceState.DUTY` (`presence.py:141`, `parade.py:252`) — the set of DUTY-state people is a strict subset of CURRENT STRENGTH. The original "unioned by person_id" wording can only ever *re-add people presence deliberately excluded*: a duty holder on approved leave (leave > duty by precedence) would be counted for breakfast while absent. Amended rule: **the meals duty term stays permanently empty; duty reaches meals exclusively through `presence_inputs` duty_day offsets in the doc builds** (roll_call(D) with duty of D−1, roll_call(D+1) with duty of D). P4.7 MUST also rewrite the misleading hook comments at `meals.py:16-18` and `:79-81` to state this — a sub-agent implements what the code comment says, not what the plan says. Pin with two tests: duty holder on approved leave is NOT counted for breakfast; stay-out CDOS with no absences is counted exactly once.

**A2 — The duty_day offset needs one owner (amends P3b.6, gates P4.7).** `presence_inputs(day)` is called twice per variant (page + finalize; six sites in `parade/routes.py`), and P3b.6's meals route adds three more doc builds. An offset convention re-derived at nine call sites by nine sub-agent moments is nine coin flips; the worst failure is silent — a roll-call page that shows duty stayers while its finalized snapshot omits them. **A3 — Adapter-row date: the natural reading is the wrong one (amends P4.7).** `covers()` compares against the **resolution day** (`presence.py:70-72`). Wrapping a duty assignment with its own `.date` makes `covers()` always False precisely when `duty_day != day` — duty would never appear at roll call, the one place it matters. **A4 — Confirm-vs-regenerate TOCTOU (amends P4.4).** `[REMOVED 2026-07-27 by decision (x): there is no confirm step to race — the fingerprint, `confirm_month` and `RosterChanged` are deleted.
